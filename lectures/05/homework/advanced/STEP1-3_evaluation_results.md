## 2. 取り方の設計（STEP 2）

### 2.3 ③-c：Graph で「問い→答え」と「先へ進む方向」を優先する

- **データの持ち方**：`graph.json` は変えない。検索のたびにコードの中で、`next_page` のつながりに向き（前→次）を付け、問いかけのページから次のページへのつながりを「問い→答え」（`answered_by`）として扱う
  - 理由：索引を作り直さずに済み、元にも戻しやすい。該当は12ページなので、毎回判定しても負担にならない
- **候補の並べ方**：今の並べ方（hop数 → 経由した用語のつながりの多さ → 入口の順位 → ID）の前に、道の種類で3段階に分ける

| 優先 | 道の種類 | 例（入口 p.40） |
|---|---|---|
| 1 | 問い→答えだけでたどった道（`answered_by`） | p.41（1 hop）、p.42（2 hop） |
| 2 | さかのぼりを含まない道（先へ進む、用語を経由する。`forward`） | 第2回 p.13 → p.14 |
| 3 | さかのぼりを含む道（`backward`） | p.39、p.38 |

- hop の上限（2）と件数の上限（10）は変えない。候補に `route` の印を付け、どの道で来たかを見えるようにした

### 2.4 ①：Tree でページを開いたら、問いかけで終わっていれば次のページも返す

- `browse_tree` でページを全文で開いたとき、問いかけのページなら、同じ資料の次のページの全文を `answer_pages` として返す。次も問いかけなら、さらに次へ（最大2ページ。Graph の hop の上限にそろえた）
- 問いかけで終わらないページや、目次のノードでは動きは変わらない

### 2.5 選ばなかった案と理由

- 同じタイトルが続くページをまとめる案：タイトルがそろっていることが前提になる。③-c はページの中身（問いかけで終わるか）だけで判断できる
- ベクトル検索に①を入れる案：宿題の「実装」の例（前後ページの本文も付ける）とほぼ同じになる
- 質問文に「問いかけのページは次のページも根拠に入れて」と書く案：改良前にも同じヒントが渡り、取り方の改良の効果と区別できなくなる

## 4. 考察

### 4.1 改善した例

- **Graph に③を入れると、p.40 の問いの答え（p.41・p.42）が、段階4・5とも上位2枠に入った。** 回答にも理由3「技術の指標だけでなく価値の指標で測る」（p.42）が入るようになった。改良前は理由1・2（p.41）で止まっていた
- さかのぼる方向のページ（p.39・p.38・第2回 p.17・p.12）が外れ、先へ進むページに入れ替わった
- 段階5の Graph は、p.41・p.42 の3つの理由（平均では分からない・非機能要件・価値の指標）がすべてそろった。9回のうちこの1回だけ
- 対照のベクトル検索・Tree・全文投入は、受け取ったページの範囲では変わらなかった（ベクトル検索の差は、モデルが選んだ検索語の違いで説明できる）
- **全文投入は、検索系の3方式がどれも取れなかった第1回 p.35 を3回とも使えた。** 一方で、p.40〜42（問い→答え）と第2回 p.14 は一度も引用しなかった。資料をすべて渡しても、モデルが全部を使うわけではない（第2回 p.15「長い文脈を、均等には使えない」の実例とも読める）

### 4.2 失敗した例・残る課題

- **Tree の①は、この質問では効く場面がなかった。** Tree は3回とも付録の章（p.70）を開き、p.40 を開かなかった。①は「開いたページの後」を補う改良なので、目次の選び方が外れると届かない。Tree の弱点は、開く前の目次選びにある
- **第1回 p.35（難しい理由の3つ）は、検索系の3方式ではどの段階でも取れなかった**（全文投入だけが使えた）。③は入口から先の広げ方の改良で、入口に入らないページには効かない
- Graph で入れ替わりに入った第1回 p.67（付録）は、用語「API」でつながっただけで質問と関係が薄い
- 問いかけの見分け方は、p.42 → p.43 のように答えでないページもつなぐ
- 受け取るページが同じでも、回答に入る理由はモデルの書き方で揺れた（Graph の段階4は非機能要件が抜け、段階5は入った）
- Tree は、読んでいないページ（第2回 p.3）を根拠に挙げたことがある

### 4.3 比べ方の限界

- 各段階1回ずつの実行で、揺れの大きさは対照の変化から推し量っただけ
- 全文投入だけ対象資料が広い（438ページ）。費用はキャッシュの効き方で大きく変わる
- 検索語はモデルが選ぶので、段階ごとに入口が変わりうる（今回は Graph の入口は同じだった）
- 質問は1問だけ。p.40 のように「問い → 次のページで答え」となる箇所を使う質問に向いた改良で、そうでない質問での効果（副作用を含む）は見ていない

### 4.4 自分の用途に採用するか（たたき台）

- **③-c は採用したい。** 講義資料や社内の説明資料のように、スライドが「問いを立てる → 次のページで答える」構成になっている資料を検索する用途では、問いのページだけを根拠に答えて肝心の答えが抜ける、という失敗が起きやすい。③-c は `graph.json` を作り直さずにコードの中だけで足せて、費用の増加もわずか
- ただし、**入口の弱さは別に手当てが要る。** p.35 のように、質問の答えそのものなのに入口に入らないページは③-c では取れない。複数の検索語で入口を集める、ベクトル検索と全文検索（キーワード）を組み合わせる、などと組み合わせたい
- **全文投入は、単独では採用しない。** p.35 を使えた点は強いが、p.40〜42 の問い→答えは一度も使わず、検索系とは別の理由に偏った。費用もキャッシュが効かなければ検索系の約8〜20倍。資料が小さく、キャッシュが効く使い方（同じ資料に続けて質問する）なら、検索系の取りこぼしを補う手段として検討の余地がある
- **Tree の①は、単独では採用しない。** 目次選びが外れると届かないため。Tree を使うなら、目次の候補に「問いかけのページ」の印を付ける、章の先頭文をもっと返す、など、開く前の選び方を先に改良したい
- 採用の前に、問いかけで終わらない質問も含めて複数の質問・複数回で測り、副作用（p.42 → p.43 のような誤ったつながり、関係の薄いページの混入）が許容できるかを確かめる
