- 気づき・疑問：
  - STEP 3 は、fetch サーバーを足す前にも同じ質問をした。そのときは用語集のツールしかなく、モデルは URL のページを読まずに「MCP とは」を推測で要約した。足した後は `fetch_fetch` で実際にページを取り、内容の違う要約になった。ツールが無くても、モデルはそれらしく答えてしまう
  - STEP 4 は、最初に日本語で検索して関係のない結果（InternalError の記事）が返り、モデルが英語で検索し直した。検索語はモデルが決めるので、ツールの側が日本語に弱いと回数と入力が増える（入力 11,091 tokens・応答3回）
  - 設定ファイルに数行足すだけで、ほかの人が作ったツールが使える。一方で、fetch のツールの説明には「元はインターネットに接続できなかったが、このツールで接続できるようになった」と、モデルの振る舞いを変える文が入っていた。ツールの説明はモデルへの指示としても働くので、足す前に中身を読む必要がある
  - AWS の URL を書き間違えたとき（`knowledge-edge-mcp`）は、エージェントの起動時に「接続できませんでした」と止まった。どのサーバーで失敗したかが表示されるので、直しやすかった
  - 疑問：URL で接続するサーバー（AWS）には、質問の内容が送られる。社内の情報を扱う質問では、どのサーバーを足してよいかの決まりが要りそう

* 気づき・疑問：
  - `raise` にすると、書いたメッセージはモデルに届かなかった。メッセージ本文はサーバー側のログ（トレースバック）には出ていたが、MCP を通ってモデルに渡ったのは「Error executing tool make_quiz」だけだった。モデルに次の行動を促したいなら、中身のあるメッセージを `return` で返すほうがよい
  - `return` 版では、モデルはツールの返り値の一覧（第1〜4回、第6回）をそのまま使って、選べる回を案内した。ツールのメッセージは、利用者向けの文というより、モデルが次に何をするかを決める材料になる
  - ツールを呼ぶかどうかは、同じ質問でも揺れた（4回中1回は呼ばなかった）。「第99回」のように明らかにありえない回だと、モデルがツールを使わずに判断することがある。範囲外の処理を確かめるには、何回か実行する必要がある
  - `make_quiz` は第3回のコードをそのまま使えた。関数を MCP サーバーに1行で登録するだけで、エージェントのコードも設定ファイルも変えずにツールが増えた
  - 用語集に第5回の用語が無かった（返り値が「1, 2, 3, 4, 6」）。第5回のクイズを頼むと範囲外になる
  - 疑問：`raise` のときにメッセージ本文が渡らないのは、MCP の決まりなのか、使っているライブラリの扱いなのか。例外のメッセージをモデルに渡す設定があるのかを調べたい。p.41に記載のある「入力ミスは、モデルが読める実行エラーにする。2025-11-25のMCP 仕様に明記されている。」という点かな。
